# 野榜队伍一键导入设计

## 目标和范围

在导航页的「队伍管理」中增加「从野榜导入」入口。读取最新野榜数据，预览队伍与成员归属变更，用户确认后一次性更新本地队伍并持久化。

本功能不自动添加播放房间，不更改主播房间号，不改动播放、弹幕、收藏和历史，也不执行持续自动分队、安装包构建或 GitHub 发布。

## 当前证据

- 2026-10-04 登录后的野榜页面显示红、黑、紫、蓝四队，各 11 人，共 44 人。
- 身份筛选显示 8 名队长、36 名队员、0 名团长。这是当前页面结果，不是永久角色规则。
- 四队筛选已经展示不同成员，之前认为筛选没有生效的判断已纠正。
- 页面 44 个主播名称经过角色后缀规范化及现有别名处理，均能对应本地 58 人导航名单。这不等于已经验证服务响应中的所有身份字段。
- 美伢Mya、可可or在网页中显示靓号，本地名单保存不同的房间号，不能只按房间号匹配。
- `MaoziRankClient` 当前以固定数组「红、蓝、黄、黑」解释数值 `team`，与页面名称不一致。页面按钮顺序不能证明服务字段的数值编码。
- `NativeTeam` 保存 `id`、`name`、`memberIds`。成员持久化仅接受内置导航名单中已知的成员 ID；本功能不扩展导航名单。
- `AppController` 已提供队伍创建、改名、删除、成员分配及工作区持久化。

## 实现前的数据契约检查

`data-team="0"` 为红队、`1` 为黑队、`2` 为紫队、`3` 为蓝队。
客户端已按此映射修正，并区分空值/缺失（未分队）与错误类型、非整数、
越界编号（未知队伍）。未分队人员在预览中单独列出并保留原归属。

实施中的只读客户端预览得到四队、36 名有效分队成员，与此前页面44人存在差异。
后续浏览器访问仍被权限策略拒绝，已停止外部核验。队长是否通过独立字段归队尚未确认，
不得根据截图编造服务字段，也不能宣称44人实时导入已完成线上验收。

2026-10-04 用户提供队长榜截图，确认以下公开房间标识与队伍归属：

- 黑队：80432（午夜抹抹茶）、6151194（本地名单为宋暖阳绝不咕咕）。
- 紫队：731252（主播帝王）、11222（王大谋QoQ）。
- 红队：2140934（老皮历险记）、2632018（归海念一刀）。

客户端只在上述8个房间的 `team` 缺失或为 null 时，使用本次截图确认的归属兜底。
服务端明确返回的有效队伍优先，即使与截图不同；错误类型或未知编号仍拒绝导入，
不通过兜底掩盖错误。普通队员和团长没有这种兜底，不新增或更改本地房间号。
这是一份当前赛事的静态业务映射，不是已经验证的动态队长字段契约。若网页改动了
队长归属而快照仍为空，客户端无法仅凭该快照发现变化，需要重新核验和更新映射。

必须通过经授权的当前数据响应或站点公开定义，验证：

1. 队伍字段的类型、编号与实际队伍名称的对应关系。
2. 主播稳定标识、名称、斗鱼标识和队伍字段的实际位置。
3. 未分队与未知队伍的表示方式。
4. 数据版本或更新标识，以及完整快照与空结果的区别。

不读取或保存浏览器密码、Cookie、Token，不将认证值、响应原文或敏感请求信息写入文档、日志或测试快照。只保存经过筛选的公共业务字段测试样例。

如果响应提供队伍配置，优先使用该配置。若只有数字编码，则根据实际证据定义映射并覆盖四个编号的测试；不得根据页面排列猜测编号。无法确认映射时，禁用导入并提示数据格式暂不支持，保留现有本地队伍。

## 成员匹配

使用内置导航成员 ID 作为写入本地队伍的唯一身份。

按以下顺序构造候选：

1. 野榜斗鱼标识与导航缓存中已确认的房间号或内置房间号精确匹配。
2. 规范化名称精确匹配：去除现有角色后缀、去除首尾空白、忽略拉丁字母大小写。
3. 应用已有的明确别名，例如「雾蒙蒙y」与「雾萌萌y」。

不同匹配途径指向不同成员、同一个成员出现多个不同队伍、多个野榜身份对应同一个成员时，视为冲突。冲突成员和未匹配成员只显示在预览中，不自动分配；不能依赖现有单值索引覆盖重复项的行为。

不模糊搜索、不按拼音猜身份、不覆盖本地房间号，也不新增主播。团长单独展示，不导入到普通队伍；角色仍由现有展示链处理，角色识别的全面改造不混入本功能。

## 导入和冲突规则

默认导入当前有效数据中的所有非空队伍，本次证据为四队。支持后续队伍名称和人数变化，不把每队 11 人写成产品限制。

- 同名本地队伍复用其 ID，比较遵循现有去空白、忽略大小写的规则。
- 缺少的队伍创建一次；重复导入相同结果不新增队伍或成员。
- 成功匹配且有有效目标队伍的主播，从旧队伍移至野榜目标队伍。
- 未成功匹配、存在冲突、没有有效队伍的主播保留原有本地归属。
- 保留其他手动队伍和所有未参与此次导入的成员；旧队伍移空后也不自动删除。
- 同名队伍中未参与此次导入的手动成员保留，预览明确显示这部分人数，因此本地队伍人数可能大于野榜人数。
- 若本地已有多个同名队伍，阻止导入并要求先消除歧义；不得任意选择一个。
- 根据实际所需新增队伍数检查现有 20 队上限，超限时整体拒绝，不部分写入。

本次导入是用户确认的快照更新，不开启后台自动覆盖。评分、状态数据的原有同步不影响此规则。

## 交互流程

1. 队伍管理中的导入按钮开始刷新野榜。请求进行中禁用重复点击。
2. 只有本次刷新成功、数据契约有效时生成预览；不能将刷新失败后保留的旧榜单当作新数据导入。
3. 在队伍管理内展示预览，避免重叠弹窗：队伍名称、来源人数、已匹配人数、保留手动成员人数及成员清单。
4. 显示新增队伍数、归属变更数、无变化人数，以及未匹配和冲突清单。未知字段、数据错误和容量错误时确认按钮不可用。
5. 提供「确认导入」和「取消」。取消不修改队伍。
6. 确认前再次检查本地队伍及用于匹配的身份与归属字段（主播标识、名称、房间号、角色、
   队伍编号/名称/有效性），并检查有效的内置/缓存房间身份集合。字段实际变化时要求重新预览。
   头像、开播状态、评分、检查时间以及榜单排序变化不使预览失效；首次缓存已有的内置房间号
   也不算身份变化。刷新进行中或刷新失败仍不可确认，身份缓存更新后必须通知确认按钮。
7. 在临时工作区副本中完成所有变更并校验，保存成功后再替换应用内快照、刷新导航页。
8. 保存失败显示固定业务错误，不改动应用内队伍，不提示导入成功。重复确认不得重复执行。

控件使用现有主题、紧凑布局和滚动列表；预览应在窗口最小尺寸下保持可读。按钮无需新增对房间或播放器的操作。

## 所有权和边界

- `MaoziRankClient`：解析和暴露经过验证的队伍标识与名称，区分刷新成功、失败和旧数据保留。
- 工作区导入逻辑：构造匹配结果、队伍变更候选及预览，保持无网络、无播放副作用，方便独立测试。
- `AppController`：协调刷新、预览有效性、确认导入、持久化和状态通知。
- `TeamManagerDialog.qml`：呈现按钮、加载状态、预览和结果，不在 QML 中实现匹配或修改队伍。
- `NativeWorkspaceStore`：沿用现有队伍保存格式，不保存认证数据或野榜响应原文。

## 验收测试

### 数据与匹配

- 四队编号分别对应经验证的当前队名；未知编号不能被当成有效队伍。
- 正常房间号、靓号名称兜底、明确别名和角色后缀可正确匹配。
- 重复身份、名称歧义、不同途径身份冲突及跨队重复成员不会被静默覆盖。
- 团长不进入普通队伍，未匹配人员不新增。

### 工作区和持久化

- 同名队伍 ID 保持稳定；重复导入无额外变更。
- 归属迁移正确，未参与导入的成员及手动队伍保留。
- 取消、刷新失败、未知队伍、容量不足、预览过期和保存失败不改动应用内队伍。
- 保存并重新加载后，队伍和成员归属一致。
- 活跃房间、房间号、收藏、历史、播放和弹幕状态不因导入变化。

### 界面与回归

- 加载状态禁用重复操作；成功后先预览，确认后才应用。
- 预览完整显示四队、成员、计数及冲突，最小窗口尺寸无截断或重叠。
- QML 引擎烟测、交互测试、视觉烟测和相关截图检查。
- 野榜客户端测试、导入逻辑测试、工作区持久化测试及控制器测试。
- Release 构建与新可执行程序自测；16 路和 24 路配置共享该功能，分别检查构建和加载。
