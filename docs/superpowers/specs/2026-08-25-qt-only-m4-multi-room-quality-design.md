# Qt-only M4 多房间播放与质量策略设计

**日期：** 2026-08-25  
**状态：** 已确认，等待实施计划  
**产品路线：** Qt + libmpv 是唯一维护版本

## 目标

在 M3 单房间远程播放生命周期之上，增加 Qt 原生多房间工作区，支持最多
9 个同时在线的直播房间，并在房间数量变化、主房间切换和单房间失败时保持
其他房间可用。

M4 只迁移历史产品中的多房间播放和自适应清晰度意图，不恢复 Electron、
Chromium 或 WebView 播放链路。

## 范围

- 最多 9 个房间；重复房间 ID 被拒绝。
- 每个房间拥有独立的播放控制器、播放表面和生命周期状态。
- 根据房间数量提供 1、2x2、3x2、3x3 网格布局。
- 支持主房间切换和用户清晰度选择。
- 5 至 9 路在线时启用主房间原画、其他房间 720p 的自动策略。
- 使用 fake StreamGet 服务覆盖并发、取消、迟到响应和错误恢复。

## 非目标

- 不使用 Electron、Chromium、Qt WebEngine、WebView、Node、React 或
  TypeScript。
- 不新增本地回环代理，不把 URL 转换为浏览器可访问地址。
- 不在自动化测试中依赖真实斗鱼网络、账号、Cookie 或凭据。
- 不在 M4 内实现弹幕协议、房间搜索目录、转码或跨平台打包重构。
- 不持久化播放 URL、查询参数、Cookie、token、签名、请求头或原始诊断。

## 架构

```text
MainWindow / workspace shell
            |
            v
MultiRoomCoordinator
            |
     1..9 RoomSession
       |          |
       v          v
RemotePlaybackController  PlayerSurface
       |
       v
StreamgetProcessClient -> MediaSource::RemoteStream -> libmpv
```

### MultiRoomCoordinator

`MultiRoomCoordinator` 是多房间工作区的唯一编排入口，负责：

- 保存房间顺序、主房间 ID 和每个房间的用户清晰度。
- 执行最多 9 个房间和重复房间校验。
- 根据在线房间数量计算每个房间的当前生效清晰度。
- 创建、删除和重排 `RoomSession`，并转发稳定的状态变化。
- 限制解析调度并确保主房间切换只刷新受影响的房间。

协调器不持有播放 URL，也不直接调用 libmpv；它只处理房间标识、质量和
生命周期命令。

### RoomSession

`RoomSession` 封装一个房间的可替换运行时状态：

- 房间 ID、显示元数据和顺序位置。
- 用户选择清晰度与当前生效清晰度。
- 当前在线/解析中/播放中/错误状态。
- 一个 `RemotePlaybackController` 和一个 `PlayerSurface`。
- 当前请求代数、取消和释放状态。

会话之间不共享播放器句柄或请求代数。销毁会话必须先停止并释放播放器，
再取消控制器请求，最后解除信号连接。

### 网格布局

使用 Qt `QGridLayout` 或同等 Qt 布局容器承载稳定的播放器槽位：

| 在线房间数 | 推荐布局 |
| --- | --- |
| 1 | 单画面 |
| 2–4 | 2x2 |
| 5–6 | 3x2 |
| 7–9 | 3x3 |

布局计算只改变槽位位置，不重建仍然存在的 `RoomSession` 或
`PlayerSurface`。播放器表面使用稳定的尺寸约束，避免状态文本、图标或清晰度
切换造成网格抖动。

## 清晰度策略

工作区为每个房间保留两个清晰度字段：

- **用户清晰度：** 用户明确选择并应在策略解除后恢复的值。
- **当前生效清晰度：** 本次解析实际使用的值。

规则如下：

1. 在线房间数为 1–4 时，每个房间使用自己的用户清晰度。
2. 在线房间数为 5–9 时，主房间使用 `Original`，其他房间使用 `720p`。
3. 切换主房间时，只重新解析新主房间和旧主房间；其他房间不重挂载。
4. 在线房间数从 5–9 降到 4 或更少时，重新解析生效清晰度发生变化的房间，
   并恢复其用户清晰度。
5. 如果请求的质量不可用，按服务返回的变体顺序选择已验证的可用变体，
   并发出固定的降级状态；不得伪造不存在的质量。

自动策略不会覆盖用户清晰度字段，也不会修改持久化工作区偏好。

## 数据流与调度

```text
添加/恢复房间
  -> coordinator 校验并创建 RoomSession
  -> 计算当前生效清晰度
  -> 解析调度器合并同房间请求
  -> StreamgetProcessClient 请求指定质量
  -> MediaSource::fromRemoteVariant() 二次校验
  -> 该房间 PlayerSurface::loadSource()
```

- StreamGet 解析并发上限为 2；同一房间的重复请求复用或取消旧请求。
- 每个房间的请求代数独立递增，迟到响应不能覆盖新状态。
- 主房间切换产生最多两个质量变化请求。
- 删除房间后，已启动但尚未返回的请求可以完成，但结果必须被丢弃。
- URL 仅在经过协议校验的 `MediaSource` 内存对象和 libmpv 调用期间存在。

## 生命周期与错误处理

### 生命周期

1. 添加房间：创建会话并开始解析。
2. 解析成功：加载远程源并进入播放状态。
3. 重新解析：递增代数、取消旧请求、只接受最新响应。
4. 删除房间：停止播放器、取消请求、释放 libmpv 表面和会话。
5. 退出应用：逐个释放会话，等待服务客户端和播放器回调清理。

### 固定错误边界

- `ROOM_OFFLINE`：房间不在线；只影响该房间。
- `TIMEOUT`：解析超时；保留其他房间运行，并允许后续重试。
- `SERVICE_FAILED`：sidecar 或协议失败；不得透传 traceback。
- `PLAYER_FAILED`：libmpv 加载或渲染失败；只将该房间置为错误状态。
- `QUALITY_UNAVAILABLE`：目标质量不可用且没有可接受回退。

错误信号只携带固定错误码或稳定用户文案。播放 URL、查询参数、Cookie、
token、签名、请求头、异常文本和原始 mpv 诊断不得进入日志、文件或 crash
artifact。

## 测试策略

### 单元测试

- 0、1、4、5、6、7、9 个房间的布局和容量边界。
- 第 10 个房间、重复房间 ID 和非法房间 ID 被拒绝。
- 1–4 路保持用户清晰度；5–9 路主房间原画、其余 720p。
- 主房间切换只刷新新旧主房间。
- 从 5 路降至 4 路恢复用户清晰度。
- 取消、删除、释放和迟到响应不会产生错误加载。

### 集成与 GUI 测试

- 9 个 fake StreamGet 请求并发完成时，各会话状态独立。
- 单房间超时、离线或播放器错误不阻塞其他房间。
- `1/4/6/9` 路网格无重叠、无尺寸抖动，删除和重排不重建剩余表面。
- 所有测试保持离线、无凭据，并扫描输出中的敏感字段。

### 受控播放验收

在明确隔离的人工或受控环境中验证：9 路均能取得首帧并持续解码；记录
CPU、GPU、内存和丢帧趋势。该验收不作为单元测试的网络依赖，也不把真实
播放地址写入证据文件。

## 验收标准

M4 只有在以下条件全部满足时完成：

1. 最多 9 个房间可独立创建、播放、切换、删除和释放。
2. 7–9 路使用稳定的 3x3 Qt 网格。
3. 自适应清晰度策略和用户清晰度恢复行为有自动化测试覆盖。
4. 单房间失败、取消和迟到响应不会污染其他房间。
5. 现有 M1–M3 构建、CTest、Python 服务测试和敏感输出扫描保持通过。
6. 没有 Electron、Chromium、WebView 或浏览器播放依赖进入新版本运行时。
