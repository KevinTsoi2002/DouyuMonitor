# Qt-only M5 直播间管理设计

**日期：** 2026-08-25  
**状态：** 已确认，待规格评审  
**产品路线：** Qt + libmpv 是唯一维护版本

## 目标

在 M4 多房间播放工作区上提供可直接操作的 Qt 原生直播间管理界面。用户可以
输入房间 ID 添加直播间，在一个固定位置管理最多 9 个房间，并修改主画面和
请求清晰度。

M5 只补齐现有 `MainWindow` 的用户操作入口。多房间会话、网格计算、播放控制和
质量策略仍由已存在的工作区层负责。

## 范围

- 主窗口右侧新增可停靠的“直播间管理”面板，默认显示且可由 Qt 标准停靠行为移动或隐藏。
- 面板提供 1 至 20 位数字房间 ID 输入和“添加”命令，默认请求清晰度为 `Auto`。
- 面板按房间加入顺序显示每个房间的管理行，且不因主画面切换改变排序。
- 每行提供设为主画面、请求清晰度选择和移除操作。
- 每行显示基础会话状态、用户请求清晰度与实际生效清晰度。
- 首个添加的房间自动成为主画面。移除主画面后，协调器沿用 M4 行为，将加入顺序中的首个剩余房间设为主画面。
- 保持 9 路容量、重复 ID 拒绝和 M4 清晰度策略：1 至 4 路使用用户请求；5 至 9 路使用主画面 `Original`、其他房间 `Standard`。

## 非目标

- 不实现直播间搜索、直播间元数据、收藏、排序持久化或工作区恢复。
- 不实现播放失败的详情、重试、自动恢复或故障诊断界面。
- 不引入 Electron、Chromium、Qt WebEngine、WebView、Node、React 或 TypeScript。
- 不在测试、日志或界面中记录播放 URL、Cookie、token、签名、请求头、原始 mpv 输出或 traceback。

## 用户界面

`MainWindow` 保持播放网格为中心区域，在右侧加入 `QDockWidget` 承载
`RoomManagementDock`。面板使用紧凑的纵向布局，避免影响 3x3 播放网格的可用空间。

### 添加区域

- `QLineEdit` 提示输入房间 ID，并使用与协调器相同的 1 至 20 位数字规则。
- “添加”是唯一的文字命令按钮；当输入为空或当前已达到 9 路上限时禁用。
- 添加成功后清空输入框并将焦点留在输入框，便于连续添加。
- 添加失败时在输入区域显示固定、安全的本地原因：`房间 ID 无效`、`房间已存在` 或 `已达到 9 路上限`。

### 房间管理行

每个房间使用一条稳定高度的行，不嵌套卡片：

- 显示房间 ID 与基础状态（`空闲`、`解析中`、`就绪`、`错误`）。错误状态不显示服务或播放器原始细节。
- 用带工具提示和无障碍名称的星标 `QToolButton` 设为主画面。当前主画面显示选中状态。
- 用 `QComboBox` 选择 `Auto`、`Original`、`Super`、`High` 或 `Standard` 作为用户请求清晰度。
- 显示实际生效清晰度；当 M4 策略替换用户请求时，使用固定“策略生效”标记，不修改下拉框中的用户选择。
- 用带工具提示和无障碍名称的移除图标按钮移除房间。

当主画面、房间数量或请求清晰度发生变化时，管理行与网格都从同一份快照刷新。移除房间会停止并释放该会话，随后播放网格按 M4 规则重新排布。

## 架构

```text
RoomManagementDock
    |  add / remove / primary / requested-quality intent
    v
MainWindow
    |  command routing
    v
MultiRoomCoordinator
    |  ordered room snapshots + M4 quality policy
    +--> RoomSession -> RemotePlaybackController -> libmpv PlayerSurface
    |
    +--> MainWindow rebuilds grid and refreshes RoomManagementDock
```

### `RoomManagementDock`

新增 `RoomManagementDock` 作为纯 Qt 展示与输入组件。它保存当前界面状态，但不保存
会话、播放器、URL 或质量策略。它发出四类信号：添加、移除、设主画面和修改用户请求
清晰度。`MainWindow` 接收这些意图并调用协调器。

`RoomManagementDock` 接收一个有序房间快照列表来刷新行。刷新必须阻断控件信号，避免
程序设置下拉框或主画面状态时重复发送用户命令。

### `MultiRoomCoordinator`

协调器继续是房间顺序、主画面、`RoomSession` 和清晰度策略的唯一事实来源。为支持 UI，
它新增以下能力：

- 返回按加入顺序排列的房间快照，字段为房间 ID、主画面标记、`RoomSession::State`、用户请求清晰度和实际生效清晰度。
- 在任何会影响快照的房间、主画面、状态或质量变化后发出统一的快照变更信号。
- 提供修改用户请求清晰度的命令。该命令更新会话保存的请求清晰度，再复用现有质量策略计算实际生效清晰度。
- 为 UI 命令提供稳定结果码，使界面能区分无效 ID、重复 ID、容量已满、未知房间和无变化请求。现有布尔 API 可以保留为兼容包装，但校验逻辑只能在协调器中实现一次。

当用户在 5 至 9 路时修改非主画面的请求清晰度，协调器保存选择但保持该房间的有效值为 `Standard`。房间数降至 4 路或以下后，协调器按 M4 规则恢复该已保存的用户请求。

### `RoomSession`

`RoomSession` 新增受控的用户请求清晰度更新入口。它不决定当前生效清晰度，也不自行重排
会话；协调器更新请求值后统一调用现有质量重算。只有实际生效清晰度改变的会话才重新解析。

## 数据流

1. 用户在面板提交操作。
2. `MainWindow` 将操作路由给 `MultiRoomCoordinator`。
3. 协调器验证请求、更新会话或主画面，并运行既有 M4 质量策略。
4. 协调器发布有序快照。
5. `MainWindow` 使用快照重建必要的网格布局并刷新管理面板。

UI 不读取 `RoomSession` 进行决策，也不重复计算容量、主画面或清晰度策略。命令在 Qt UI
线程中完成同步校验；远程解析继续由现有会话生命周期异步处理。

## 错误处理与安全

- 面板将本地可解释的命令结果映射为固定用户文案；不会根据布尔失败结果猜测原因。
- 运行中的解析或播放器失败只显示现有基础 `错误` 状态，且不新增重试按钮。
- 删除、切换主画面和切换清晰度沿用 M4 的请求代数、取消和迟到响应保护。
- UI 快照和测试断言只使用房间 ID、枚举状态、清晰度和固定错误码。

## 测试策略

### 协调器与会话单元测试

- 修改 1 至 4 路房间的请求清晰度时，用户请求和实际生效值同步更新。
- 5 至 9 路时，非主画面修改请求后保存请求值但保持 `Standard`；回到 4 路时恢复请求值。
- 修改主画面后，快照中只有主画面标记和受质量策略影响的有效值变化。
- 无效 ID、重复 ID、第 10 个房间、未知房间和重复主画面请求返回稳定结果码。
- 每种影响状态的操作都会发布与当前协调器查询结果一致的有序快照。

### Qt UI 测试

- 输入框、添加按钮和容量禁用状态符合房间 ID 与 9 路规则。
- 添加、移除、设主画面和质量选择各发送一次正确意图。
- 快照刷新更新所有管理行，且不会回发用户信号。
- 实际生效质量不同于用户请求时显示策略标记；下拉框仍保留用户请求。
- 错误状态不显示动态服务文本或播放器诊断。

### 回归验证

- MSVC x64 配置与原生构建通过。
- CTest 全量通过，Python StreamGet 服务测试通过。
- 离线测试输出执行敏感字段扫描，确认没有 URL、Cookie、token、签名、请求头、traceback 或原始 mpv 诊断。
- 现有 M1 至 M4 的单房间、网格、容量、删除和质量策略测试保持通过。

## 验收标准

M5 在满足以下条件后完成：

1. 用户可通过主窗口右侧面板直接添加、移除和管理 1 至 9 个数字房间 ID。
2. 用户可设定主画面并为每个房间保存请求清晰度。
3. 面板准确显示 M4 策略产生的实际生效清晰度，且不会覆盖用户请求。
4. 重复 ID、无效 ID 和第 10 个房间得到明确且安全的本地反馈。
5. 网格继续按 M4 规则运行，未引入浏览器运行时或网络依赖。
6. 自动化测试、原生构建和敏感输出扫描均通过。
