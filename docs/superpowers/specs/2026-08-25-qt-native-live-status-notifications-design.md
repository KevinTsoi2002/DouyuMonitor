# Qt 原生直播状态与 Windows 通知设计

**日期：** 2026-08-25  
**状态：** 已确认，待规格评审  
**产品路线：** Qt + libmpv 是唯一维护版本

## 目标

在已确认的 Qt 原生旧版工作区布局中，为左侧房间列表提供主播开播状态，
并在应用运行期间通过 Windows 系统通知告知用户四类状态转移：开播、下播、
播放失败和播放恢复。

状态显示、轮询和通知必须适用于最多 9 个受管房间。应用关闭后停止轮询和
通知，不添加后台驻留服务、常驻进程或 Electron 兼容层。

## 范围

- 左侧房间列表每行显示独立的直播状态：`直播中`、`未开播` 或 `状态待确认`。
- 直播状态使用绿色、红色或灰色状态点，并提供状态文字和无障碍名称。
- 播放失败与直播状态分离：房间保持开播时，解析或播放器异常显示固定警告图标；
  不将异常文本、播放地址或服务诊断显示给用户。
- 在线房间每 60 秒刷新一次房间资料；离线房间每 120 秒刷新一次。
- 刷新失败使用 30、60、120、240 秒退避；每个房间独立错峰，同一房间不并发刷新。
- 开播后自动按该房间当前有效清晰度重新解析并播放；下播后停止该房间播放，
  但保留房间、分组、收藏、排序、请求清晰度、主画面和音频设置。
- Windows 系统通知默认开启，并在设置中提供总开关和开播、下播、播放失败、
  播放恢复四个独立事件开关。设置持久化到 `QSettings`。
- 同一房间同一通知事件 5 分钟内去重；全局最多 6 条通知/分钟。抑制的通知不排队补发。

## 非目标

- 不在应用退出后继续检测或发送通知。
- 不实现通知历史、通知点击跳转、声音、自定义通知模板或跨设备同步。
- 不加入 Electron、Chromium、Qt WebEngine、WebView、Node、React 或 TypeScript。
- 不把播放 URL、查询参数、Cookie、token、签名、请求头、原始 traceback 或原始
  mpv 输出写入界面、通知、设置、测试输出或实施日志。

## 用户界面

左侧房间列表沿用已确认的旧版布局。每个房间行将主播名与房间 ID 保持为主识别信息，
在副标题区域加入状态文字和颜色点：

- `直播中`：绿色状态点；可操作的播放器仍显示原有播放状态。
- `未开播`：红色状态点；播放画面显示离线状态，不移除该房间。
- `状态待确认`：灰色状态点；用于首次加入、首次恢复和临时资料刷新失败。
- 播放异常：保留上述直播状态，在行尾显示警告图标。工具提示使用固定、安全文案，
  例如“播放异常，正在等待下一次状态刷新”。

状态文字不使用弹窗，不改变房间行高度，也不抢占主画面、音频或清晰度控件。
通知设置位于 Qt 原生设置入口，使用一个总开关和四个独立复选项。关闭总开关会禁用
事件复选项但保留其设置；重新打开后恢复各事件的上次选择。

## 架构

```text
RoomSidebar
    ^                               |
    | ordered room snapshots         | room actions
    |                               v
MainWindow <---------------- MultiRoomCoordinator
                                  |        |
                                  |        +--> RoomSession -> RemotePlaybackController -> libmpv
                                  |
                                  +--> RoomStatusScheduler
                                  |        |
                                  |        +--> StreamgetProcessClient.search(roomId)
                                  |
                                  +--> NotificationPolicy
                                           |
                                           +--> WindowsNotificationService
                                                  -> QSystemTrayIcon::showMessage
```

### `RoomSession`

`RoomSession` 保留播放生命周期，并新增一个独立的直播状态字段：
`Unknown`、`Online`、`Offline`。它同时持有经过校验的房间资料快照：房间 ID、主播名、
标题、分区、观众文本和头像 URL。没有资料时，房间 ID 是界面的安全回退名称。

`RoomSession` 不自行轮询，不自行发送通知，也不决定刷新间隔。解析结果中的
`ROOM_OFFLINE` 会被映射为 `Offline`，而非播放失败；其他解析、加载或播放器失败
保留为播放状态错误。

### `RoomStatusScheduler`

新增一个由 `MultiRoomCoordinator` 拥有的调度器。它为每个当前受管房间维护独立状态：
正在请求标记、失败次数、下一次定时器、请求 ID 和房间生命周期代数。

- 房间加入后，现有播放解析立刻开始；调度器同时安排资料刷新，以补足主播资料。
- 在线房间按 60 秒刷新，离线房间按 120 秒刷新。
- 每个基础间隔加入基于房间 ID 的小幅确定性错峰，避免九个房间同时请求。
- 资料刷新失败不会覆盖最后一次确定的在线/离线状态；首次尚无确定状态时显示
  `Unknown`。失败按 30、60、120、240 秒退避，成功后清零失败计数。
- 调度器不为同一个房间并发发起请求。移除房间、应用销毁或会话代数变化时取消请求并
  清理定时器；迟到响应必须忽略。

调度器通过现有 `StreamgetProcessClient.search(roomId)` 使用数字房间查询取得公开房间资料。
客户端继续保持两路在途请求上限；刷新调度不得绕过其队列或增加第二个网络客户端。

### `MultiRoomCoordinator`

协调器仍是房间顺序、会话、主画面和实际生效清晰度的唯一事实来源。它扩展为发布一个
UI 安全的有序快照，其中包含当前 `RoomSession` 状态、直播状态、显示资料和播放健康状态。
任何有效的资料、直播、播放、质量或房间集合变化均通过同一个快照更新左侧列表和网格。

当直播状态从 `Offline` 到 `Online` 时，协调器使用既有质量策略请求重新解析；当状态从
`Online` 到 `Offline` 时，它取消当前解析并停止该房间播放器，但不会删除会话或用户偏好。
任何自动播放操作都必须验证房间仍存在且请求代数仍匹配。

### `NotificationPolicy`

新增纯 C++ 策略类，输入当前有序房间快照和可注入时钟，输出安全的通知事件。它维护前一份
快照作为基线：首次输入、房间加入、房间移除、应用恢复和工作区重建只更新基线，不补发历史事件。

仅下列转移会生成事件：

| 事件 | 转移 |
| --- | --- |
| 开播 | `Offline -> Online` |
| 下播 | `Online -> Offline` |
| 播放失败 | 非故障播放状态进入故障状态，且直播状态不是 `Offline` |
| 播放恢复 | 故障或恢复中状态重新进入稳定播放 |

事件的标题和正文只使用主播名、房间 ID 和固定文案。没有主播名时使用“房间 <ID>”。
策略以 `roomId:eventType:diagnosticCode` 作为去重键，同一键在 5 分钟内仅发送一次；
最近 60 秒已发送 6 条时拒绝后续事件。被拒绝事件只更新状态基线，不进入队列。

### `WindowsNotificationService`

新增一个小型 Qt 适配器，负责读取 `QSettings`、判断事件开关，并通过
`QSystemTrayIcon::showMessage` 发送 Windows 系统通知。`MainWindow` 持有该适配器所需的
应用托盘图标；图标只在应用运行时存在，窗口关闭时随进程退出。

系统环境可能关闭通知或不支持消息显示。适配器在该情况下安静降级：不阻塞轮询、播放或
房间状态更新，不将同一事件改为模态弹窗。左侧列表始终保留应用内可见状态。

## 数据流

1. 用户添加房间后，协调器创建会话并立刻按有效清晰度发起播放解析。
2. 调度器为该房间安排资料刷新；`StreamgetProcessClient` 返回经过协议校验的资料结果。
3. 协调器验证请求 ID 和房间代数，更新会话的资料与直播状态，并发布有序快照。
4. 若在线状态发生转移，协调器停止或重新启动对应播放会话。
5. 协调器将快照交给 `NotificationPolicy`。策略只对合法状态转移输出未被去重或限流的事件。
6. `WindowsNotificationService` 读取持久化开关，向 Windows 发送允许的事件；无论通知是否
   送达，左侧列表的状态都已更新。

## 错误处理与安全

- 资料请求失败只使用固定错误类别，不能覆盖最后的有效在线状态或暴露服务输出。
- `ROOM_OFFLINE` 不是播放失败通知；它只参与离线状态转移。
- 房间被移除后，所有定时器、请求映射和通知基线立即清理。任何迟到响应不得恢复房间或触发通知。
- 通知发送失败不自动重试当前事件，也不影响后续状态轮询。
- 设置损坏、缺失或版本不匹配时恢复默认值：总开关开启，四类事件开启。
- `QSettings` 只保存通知偏好，不保存通知历史、房间资料中的敏感字段或播放源。

## 测试策略

### 纯逻辑测试

- `NotificationPolicy`：首帧基线无通知、四类状态转移、`ROOM_OFFLINE` 排除播放失败、
  5 分钟去重、6 条/分钟限流、房间移除和重新加入不补发。
- `RoomStatusScheduler`：在线/离线间隔、确定性错峰、退避、同房间无并发、取消和迟到响应隔离。
- 协调器：离线停止播放、开播按有效清晰度重新解析、请求代数保护、快照排序与显示回退。
- 偏好：默认值、完整读写、总开关与事件开关关系、非法设置回退。

### Qt 组件与集成测试

- 左侧列表为 `Online`、`Offline`、`Unknown` 和播放错误显示正确文字、图标、工具提示和无障碍名称。
- 资料刷新成功会更新主播名和状态，失败不会清空上次有效资料。
- 伪造 Windows 通知适配器验证开关、事件文本、去重后调用次数和不支持环境的无异常降级。
- 移除房间后，网格、列表、定时器和通知基线一致；迟到响应无可见影响。

### 回归验证

- MSVC x64 原生构建和全量 CTest 通过。
- Python StreamGet 服务测试继续通过。
- 使用离线 fake StreamGet 子进程覆盖所有状态转移；不进行真实斗鱼请求或真实九路播放烟测。
- 对新增源码、测试输出和实施日志执行敏感字段扫描，确认未包含播放 URL、Cookie、token、签名、
  请求头、traceback 或原始 mpv 诊断。

## 验收标准

1. 最多 9 个受管房间都能在左侧列表中显示独立、稳定的主播直播状态。
2. 在线、离线、首次确认、资料刷新失败和播放错误不会相互覆盖或产生错误的自动播放行为。
3. 开播、下播、播放失败和播放恢复仅在应用运行时经 Windows 系统通知发送。
4. 首次加载、房间加入、删除、恢复和频繁刷新不会产生历史通知或通知洪泛。
5. 总开关、四个事件开关、5 分钟去重和 6 条/分钟限流均有效，并跨重启保留。
6. 不引入浏览器运行时、后台服务或敏感数据记录；原生构建、离线测试和安全扫描通过。
